# T15 plan: Bluesky source adapter

Issue: #71. Status: plan only. Nothing is built until Aiman approves this plan.

## Summary

Add a `BlueskyAdapter` that polls the public, unauthenticated `app.bsky.feed.getAuthorFeed` endpoint for a short, operator-configured list of Bluesky accounts. It sits behind `FEATURE_BLUESKY` (default `false`), registers as one OSINT source, and needs no new dependency, because `requests` is already in `ai-brain/requirements.txt`. It does not use Bluesky keyword search. Unauthenticated search is currently blocked or unreliable, and authenticated search would bring a stored account secret into the OSINT module (details below).

## What I verified about the Bluesky API (checked 2026-11-05)

Sources were the official docs and public issue trackers. I did not send a live request from this session (see "Could not verify").

1. **Public reads need no auth.** Bluesky's API reference says most `app.bsky.*` GETs "are public and can be called without authentication against the Bluesky AppView at `https://public.api.bsky.app`" ([API reference](https://docs.bsky.app/docs/api/app-bsky-feed-get-author-feed), [API hosts and auth](https://docs.bsky.app/docs/advanced-guides/api-directory)). The rate-limit page calls the AppView limits "generous" without giving numbers, and asks "public web" use cases to use the cached `public.api.bsky.app` host ([rate limits](https://docs.bsky.app/docs/advanced-guides/rate-limits)). The published 3000 requests per 5 minutes per IP limit applies to authenticated PDS traffic.
2. **`getAuthorFeed` is explicitly "Does not require auth"** in its lexicon ([getAuthorFeed.json](https://github.com/bluesky-social/atproto/blob/main/lexicons/app/bsky/feed/getAuthorFeed.json)). Parameters: `actor` (handle or DID, required), `limit` 1 to 100 (default 50), `cursor`, `filter` (`posts_no_replies` and others), and `includePins` (default false). The response is `{cursor?, feed: [FeedViewPost]}`. Each `FeedViewPost` has `post` (`uri`, `cid`, `author`, `record`, `indexedAt`, `labels`) and an optional `reason` (repost or pin). The post text is `post.record.text`, and `record.createdAt` is set by the client.
3. **Reposts appear under every filter**, including `posts_no_replies`, and their `post.author` is the original author, not the watched account. An unknown actor returns HTTP 400 `Profile not found`.
4. **Keyword search (`app.bsky.feed.searchPosts`) is not dependable without auth.** It is documented as public, but it has returned 403 ("Request forbidden by administrative rules") on `public.api.bsky.app` since early 2025, and on `api.bsky.app` too, intermittently, since August 2026 ([bsky-docs#332](https://github.com/bluesky-social/bsky-docs/issues/332)). Cursor pagination on it is blocked outright. A Bluesky engineer said search was degraded because people use it "to keep up with all posts, instead of using the firehose" ([atproto#2838](https://github.com/bluesky-social/atproto/issues/2838)), which is exactly what a polling OSINT loop would do.
5. **Authenticated search** needs a Bluesky account and an app password, a `com.atproto.server.createSession` call (limited to 30 per 5 minutes and 300 per day per account), and token refresh handling.
6. **Jetstream / firehose** is unauthenticated, but it is a WebSocket stream of the whole network. It needs a WebSocket client dependency and does not fit the `SourceAdapter.poll()` model.
7. **Accounts can self-label `!no-unauthenticated`** to ask not to be shown to logged-out viewers. The AppView still returns their posts to unauthenticated callers, so the client has to honor the label itself.
8. **Developer Guidelines** rule 3: "All services must have a method for deleting content a user has requested to be deleted" ([guidelines](https://docs.bsky.app/docs/support/developer-guidelines)). This matters because `ai-brain/osint_agent.py` copies the raw alert text into `system_logs.message`, and that table has no soft delete (`docs/OWASP_AUDIT.md`, Data privacy).

## Options considered

- **A. `getAuthorFeed` watchlist (recommended).** Documented as no-auth, stable, and a plain GET that fits `poll()`. The trade-off is that it only sees the accounts listed in `BLUESKY_ACTORS`, not the whole network. For the demo, the team posts from its own Bluesky account, the same way the ntfy demo uses a team topic. A narrow watchlist is also easier to defend ethically than network-wide keyword monitoring.
- **B. Unauthenticated `searchPosts`.** Rejected: it 403s intermittently today, and Bluesky has said this use is unwelcome.
- **C. Authenticated `searchPosts`.** Rejected for T15: it adds a secret (`BLUESKY_APP_PASSWORD`), session handling, and an A07 surface, and it is still the use Bluesky discourages. It could be a later task behind its own flag if Aiman wants keyword coverage.
- **D. Jetstream.** Rejected: new dependency, a streaming model, and whole-network volume.
- **E. Python `atproto` SDK.** Rejected: one GET does not justify the package and its transitive dependencies. `requests` is already used by the ntfy and RSS adapters.

## Design

### New file `ai-brain/bluesky_adapter.py`

`BlueskyAdapter(SourceAdapter)`, in the same shape as `ntfy_adapter.py` and `rss_adapter.py`:

- `SOURCE_NAME = "bluesky-watchlist"`, `DEFAULT_APPVIEW = "https://public.api.bsky.app"`, `PAGE_LIMIT = 25`, `MAX_ACTORS = 10`, `MAX_AGE = timedelta(minutes=10)`.
- `__init__(appview, actors, timeout=10.0, clock=None)`: strips the URL and actor values, then raises `ValueError("BLUESKY_ACTORS is not set.")` when the list is empty and `ValueError` when it has more than `MAX_ACTORS` entries. `main._start_live` already turns `ValueError` into a clean exit code 1, the same way a missing `NTFY_TOPIC` is handled.
- `from_env()`: reads `BLUESKY_APPVIEW_URL` and `BLUESKY_ACTORS` (comma-separated).
- `registration_payload()`: `source_type` `"Social Media"`, `url` `<appview>/xrpc/app.bsky.feed.getAuthorFeed`, `reliability_score` `0.5` to match the other adapters (open question 2).
- `_fetch_items()`: for each actor, one `requests.get(url, timeout=...)` to `<appview>/xrpc/app.bsky.feed.getAuthorFeed?actor=<actor>&limit=25&filter=posts_no_replies`, built with `urlencode` like the ntfy adapter. It sends no auth header and no cursor. Deduplication on `post.uri` comes from the base class `_seen_ids`.
  - Per-actor failure: a `requests.RequestException` for one actor is logged as a warning (actor and status code, no response body) and that actor is skipped. If every actor fails in the same poll, the last exception is re-raised, so `LiveOsintRunner._new_items` reports it the way it does for ntfy and RSS today.
- Parsing (small helpers to stay under complexity 10 and cognitive 15):
  - Invalid JSON, or a missing or non-list `feed`, yields no items.
  - Skip any entry that has a `reason` (reposts and pins). A repost carries someone else's text, and this keeps each item attributable to the watched account.
  - Skip records whose `$type` is not `app.bsky.feed.post`, empty text, a `uri` that does not start with `at://`, and authors labeled `!no-unauthenticated`.
  - `external_id = post.uri`, `text = record.text.strip()`.
  - `timestamp = post.indexedAt` (set by the AppView), parsed with `datetime.fromisoformat` and falling back to the current time in UTC. **Not `record.createdAt`**, because that field is client-set and a backdated or future-dated post could pull an item into or out of the corroboration window.
  - Drop posts indexed more than `MAX_AGE` before the poll. The first page can hold 25 old posts, and this avoids classifying them all on startup, which matches the ntfy adapter's `since=10m`.

### Corroboration

The adapter registers one source id for every watched account. Two Bluesky accounts can therefore never corroborate each other, so Bluesky alone cannot activate a camera, and a pair of sockpuppet accounts cannot either. A Bluesky post still corroborates with an ntfy or RSS report of the same class. Invariant 6 and `corroboration.py` are unchanged.

### Wiring

- `ai-brain/osint_settings.py`: add `bluesky_enabled()`, parsed the same way as `live_osint_enabled()`.
- `ai-brain/live_osint.py`: `_select_adapters` appends `BlueskyAdapter.from_env()` when `bluesky_enabled()` is true. Injected adapters (as in tests) are unchanged. With the flag off, the default list stays ntfy plus RSS.
- `FEATURE_BLUESKY` only has an effect when `FEATURE_LIVE_OSINT=true`. The mock JSON path never reads it.

### `ai-brain/.env.example` additions

```
# Bluesky stays off unless this is true. Needs FEATURE_LIVE_OSINT=true.
FEATURE_BLUESKY=false
BLUESKY_APPVIEW_URL=https://public.api.bsky.app
# Comma-separated handles or DIDs, at most 10. Use accounts the team owns or public agency accounts.
BLUESKY_ACTORS=replace-with-demo-handle.bsky.social
```

## Tests (synthetic data, no network)

Fixture `ai-brain/tests/fixtures/bluesky_author_feed.json`, a hand-written `getAuthorFeed` response using `.test` handles and fake `did:plc:` ids. It holds one normal post, one repost, one pin, one non-post record, one empty-text post, one `!no-unauthenticated` author, one post older than `MAX_AGE`, and one duplicated `uri`.

New `ai-brain/tests/test_bluesky_adapter.py`, with `bluesky_adapter.requests.get` monkeypatched:

1. A normal post becomes a `SourceItem` with the `at://` uri, stripped text, the `indexedAt` timestamp, and `source_name == "bluesky-watchlist"`.
2. Reposts, pins, non-post records, empty text, `!no-unauthenticated` authors, and posts older than `MAX_AGE` are skipped.
3. A second poll of the same page yields nothing.
4. The request URL has the configured host, the `getAuthorFeed` path, `actor`, `limit=25`, and `filter=posts_no_replies`, the timeout is 10, and no `Authorization` header is sent.
5. One actor returning HTTP 400 is logged and skipped while the other actor's posts still come through. When every actor fails, the error is raised.
6. Invalid JSON or a missing `feed` yields no items.
7. `from_env`: an empty `BLUESKY_ACTORS` raises `ValueError`, more than 10 actors raises `ValueError`, and whitespace and blank entries are trimmed.
8. `bluesky_enabled()` defaults to false.

Additions to `ai-brain/tests/test_live_osint.py`:

9. With `FEATURE_BLUESKY` unset, the default adapters are only ntfy and RSS (the existing `test_default_adapters_poll_ntfy_and_rss` must still pass unchanged).
10. With `FEATURE_BLUESKY=true`, the runner also requests the Bluesky URL.
11. A Bluesky item plus a `StaticAdapter` item of the same class, using `ScriptedAgent`, corroborate and activate camera 1. Two Bluesky actors reporting the same class do not.

## Open questions for Aiman

1. Is a watchlist of named accounts acceptable instead of keyword search? For the demo, it means someone posts the tip from a team-owned Bluesky account.
2. Should `reliability_score` stay at `0.5` like ntfy and RSS, or go lower for social media?
3. Are the limits right: at most 10 accounts, 25 posts per page, and a 10-minute startup window? At the default 5-second poll, 10 accounts means about 120 requests per minute to the AppView.
4. Is the deletion gap acceptable as a documented OWASP open item for the course, or should the build also strip post text from the system log message for Bluesky items?
