## Problem

`POST /auth/login` accepts unlimited attempts (`docs/OWASP_AUDIT.md`, A07, "Remaining gap"). Each attempt for an existing user runs an Argon2 verify, so the route is open to both password guessing and CPU exhaustion. The console already maps HTTP 429 to "Too many attempts. Please try again later." (`frontend/heimdall_console.html`), but the API never returns 429.

## Facts the design depends on

1. **One process.** `docker-compose.yml` and `backend/Dockerfile` start a single `uvicorn` process with no `--workers` flag, so in-process state is shared by every request.
2. **No proxy.** The browser, `ai-brain/osint_client.py`, and `vision/vision_client.py` call the API directly, so `request.client.host` is the peer address and `X-Forwarded-For` must not be trusted.
3. **Under Docker Desktop, every host client shares one IP.** The local API log shows console traffic arriving from `192.168.65.1`. The operator's browser, the OSINT runner, and the vision client all run on the host, so they share that address. A limit keyed by IP alone works out to a single global limit for the demo.
4. **Service accounts log in once at startup.** `ai-brain/main.py` and `vision/main.py` call `authenticate()` once. A non-200 response raises `HeimdallAPIError` through `_ensure_success`, so a 429 fails loudly without any client change. A token already issued keeps working for `JWT_ACCESS_TOKEN_MINUTES`.
5. **FastAPI runs sync routes in a thread pool.** `login_user` is a sync function, so shared state needs a lock.

## Options considered

- **A. In-memory failure counter in a new backend module (recommended).** No new dependency, no migration, and about 80 lines plus tests. State is lost on restart and is not shared across workers. That is acceptable while the API runs as one process, and the plan records it as a known limit.
- **B. `slowapi` (wraps `limits`).** It limits every request to a route, not just failures, so a legitimate operator who logs in repeatedly gets throttled while failure-only logic still has to be written by hand. It also adds two dependencies. Rejected.
- **C. Database-backed attempt table.** Survives restarts and works with multiple workers, but needs `models.py` and an Alembic migration (both protected paths) plus a write on every failed login. Worth revisiting only if the API moves to several workers. Rejected for now.
- **D. Hard account lockout (disable the user after N failures).** Anyone who knows the OSINT or vision service username could lock it out from anywhere, which stops the pipeline on its next restart. Rejected in favor of a temporary per-(IP, username) block that expires on its own.

## Design (option A)

### New file `backend/app/rate_limit.py`

`LoginRateLimiter`, with a docstring that includes `Args:` and `Returns:`:

- `__init__(max_failures, ip_max_failures, window_seconds, clock=time.monotonic)`. The injectable clock lets tests skip ahead without sleeping.
- State: two `dict[key, collections.deque[float]]` of failure timestamps, one keyed by `(ip, username)` and one keyed by `ip`, guarded by a `threading.Lock`.
- `retry_after(ip, username) -> int | None`: prunes timestamps older than the window, then returns the seconds until the oldest relevant failure expires if either count is at its limit. Otherwise it returns `None`.
- `record_failure(ip, username) -> None`: appends `now` to both deques.
- `record_success(ip, username) -> None`: clears the `(ip, username)` deque. The IP deque is left alone, so one valid login cannot reset an attacker's spray across other usernames.
- `reset() -> None`: clears everything (used by tests).
- Memory bound: `record_failure` drops empty deques during pruning and, once there are more than 10,000 keys, evicts the key whose newest failure is oldest. A spray of random usernames cannot grow memory without bound.
- `from_env()`: reads the three variables below. A value of `0` for `LOGIN_MAX_FAILURES` disables the limiter (an emergency switch, not the default).
- Module-level `login_rate_limiter = LoginRateLimiter.from_env()`.

The key username is `login_data.username.lower()`, the same normalization `login_user` already uses. The schema caps it at 100 characters.

### Change to `backend/app/auth.py` (protected path; about 10 lines)

`login_user` gains a `request: Request` parameter and keeps its current behavior otherwise:

1. Read `ip = request.client.host if request.client else "unknown"`.
2. **Before** the user lookup and the Argon2 verify, call `retry_after`. If it returns a value, raise `HTTPException(429, detail="Too many failed login attempts. Try again later.", headers={"Retry-After": str(seconds)})`. Checking first also stops a blocked caller from burning Argon2 CPU.
3. On the existing failure branch, call `record_failure`, then raise the same `authentication_error()` as today.
4. On success, call `record_success`, then return the token.

The 429 body is the same whether or not the username exists, so it leaks nothing new. Blocked attempts are not recorded, so a block lasts at most one window after the last real failure.

### Logging

`logging.getLogger(__name__)` in `rate_limit.py` emits one `WARNING` when a key first reaches its limit, including the client IP, the lowercased username, and which limit tripped. It never logs the password or the request body. This adds a security event to A09 without logging every failed attempt.

### Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `LOGIN_MAX_FAILURES` | `5` | Failures per (IP, username) inside the window before 429. `0` disables the limiter. |
| `LOGIN_IP_MAX_FAILURES` | `50` | Failures per IP across all usernames inside the window. |
| `LOGIN_FAILURE_WINDOW_SECONDS` | `900` | Sliding window length. |

The per-IP cap is deliberately loose because of fact 3. At 50, a mistyped password never trips it, and a spray is still capped at 200 guesses an hour per IP instead of being unlimited.

All three go into the root `.env.example`, under the existing JWT block, in the same PR (invariant 4). The code defaults apply inside Docker without editing `docker-compose.yml`. Making the values tunable in the container would mean adding them to the `api.environment` block, which is a protected file. That is left as a follow-up that needs its own approval, not part of this change.

This is a finished security control, not an incomplete feature, so it ships on by default rather than behind a `FEATURE_*` flag (invariant 5 covers incomplete features).

## Tests (`backend/tests/test_rate_limit.py`, synthetic data, no network)

Unit tests on `LoginRateLimiter` with a fake clock:

1. Below `max_failures`, `retry_after` returns `None`.
2. At `max_failures` for one (IP, username), it returns a positive number of seconds, and the same username from another IP is not blocked.
3. Once the window passes, the block lifts with no further calls.
4. `record_success` clears that (IP, username) but not the IP count.
5. The IP cap trips on failures spread across different usernames.
6. `max_failures = 0` never blocks.
7. Eviction keeps the key count at or under the cap.

Route tests through `unauthenticated_client`, with the env set to small limits:

8. N wrong passwords return 401, and the next attempt returns 429 with `Retry-After` and the generic detail, **even with the correct password**.
9. An unknown username is blocked the same way, with an identical 429 body (no enumeration).
10. A successful login before the limit resets the per-user count.
11. All existing `test_auth.py` tests still pass unchanged.

`conftest.py` gains an autouse fixture that calls `login_rate_limiter.reset()` before each test, so module-level state never leaks between tests. Backend tests need Postgres and `alembic upgrade head`, as `scripts/check` already sets up.

## Out of scope (separate issues for Arham if wanted)

- **Login timing for unknown users.** `login_user` skips `verify_password` when the user does not exist, so response time can reveal valid usernames. A dummy Argon2 verify on that path would close it.
- **Throttling `POST /auth/register`.** Registration is on by default (A01), so it may deserve the per-IP limit too.
- Token revocation and logout, OAuth, and multi-worker or shared-store limiting.

- Six failed logins for one username from one client return five 401s and then a 429 with `Retry-After`.
- A correct password during the block still returns 429. After the window passes, it returns 200.
- OSINT and vision start normally when their credentials are right, and fail with a clear `HeimdallAPIError` while blocked.
- `bash scripts/check` passes. Ruff (complexity 10) and complexipy (15) stay clean.
