# T16 plan: vision trigger-driven activation

Issue: #34. Status: plan only, waiting for Aiman's approval. Nothing under `vision/` changes in this PR.

## Why this is a plan first

`docs/agent/TASKS.md` marks T16 plan-first because it changes `vision/` from a run-once script into a long-running process that opens a webcam. It also changes who controls camera state, which is a security-relevant behavior change (AGENTS.md invariant 8).

## Dependency status

T16 depends on T02 (pipeline E2E). T02 is not merged: `agent/T02` has no commits beyond `main` at the time of writing. The unit tests in this plan do not need T02. Only the optional end-to-end test at the end does. Aiman decides whether the build waits for T02 (see Open questions).

## What the code does today

- `vision/main.py` `VisionPipelineApp.run()` logs in, sets camera 1 `Active` (`_set_camera_mode("Active")`), runs YOLOv8n over every image in `vision/test_media/`, posts each detection as a threat event and a system log, then sets camera 1 `Dormant` in a `finally` block. Vision decides when the camera is active.
- `vision/vision_client.py` `set_camera_state()` does `GET /camera-states/{id}`, then `POST` (if 404) or `PUT`. It is covered by `backend/tests/test_vision_client.py`.
- `vision/detector.py` has the `FrameSource` interface, `StaticImageSource`, and `ThreatDetector`. It imports `cv2` and `ultralytics` at module load.
- `ai-brain/camera_activation.py` `CameraActivator._activate_camera()` already does `PUT /camera-states/{camera_id}` with `mode=Active, fps=5, resolution=720p` when `CorroborationTracker` fires. Nothing sets the camera back to `Dormant` after that. T14's `scripts/demo_reset.sh` will do it for demos.
- `backend/app/seed.py` seeds camera 1 as `Active`, cameras 2 and 3 as `Dormant`.
- There is no `vision/tests/`. The CI `vision` job already runs `pytest vision/tests -q` once that folder exists (`.github/workflows/ci.yml`, "Run vision tests" step). `scripts/check` does not run vision tests.

## Design

### Trigger contract: camera state is the only signal

Vision stays an HTTP client of the backend (invariant 1). It never imports `ai-brain/`. The trigger is the existing row OSINT already writes:

1. OSINT corroborates (two distinct source ids, same class, inside the window; invariant 6 unchanged) and `CameraActivator` PUTs camera N to `Active`.
2. Vision polls `GET /camera-states/{VISION_CAMERA_ID}` every `VISION_STATE_POLL_SECONDS`.
3. While the mode is `Active`, vision opens its frame source, runs YOLOv8n, and posts detections. While `Dormant`, it releases the source (the webcam light goes off) and only polls.

Vision becomes read-only on camera state: it never calls `POST` or `PUT /camera-states`. If the camera row does not exist (404), vision logs a warning and keeps polling. Seed, an operator, or the console registers the camera.

No backend, schema, migration, or `ai-brain/` change is needed. `CameraActivator` already writes the trigger.

### Runner loop

New `vision/vision_runner.py` with `VisionRunner`, shaped like `LiveOsintRunner` (`ai-brain/live_osint.py`) so tests can drive it:

```text
VisionRunner(client, detector, source, settings, sleep=None, clock=None)
run(max_cycles=None) -> int
  each cycle:
    mode, fps = client.get_camera_state(camera_id)    # None on 404
    if mode == "Active":
        source.open() if not open
        process frames for up to VISION_STATE_POLL_SECONDS, paced at the row's fps
    else:
        source.close() if open
        sleep(VISION_STATE_POLL_SECONDS)
  finally: source.close()
```

- Frame pacing uses the `fps` value on the camera row (CameraActivator writes 5), so the operator-visible fps is what vision actually does.
- `sleep` and `clock` are injected so tests run instantly. `max_cycles` bounds test runs.
- `KeyboardInterrupt` closes the source and returns 0, matching `LiveOsintRunner.run()`.
- New log events use `logging`, not `print` (AGENTS.md code style). A short startup banner can stay as console output.

### Frame sources

Move frame sources out of `detector.py` into a new `vision/frame_sources.py`, so the runner and tests never import `ultralytics`:

- `FrameSource` gains an explicit lifecycle: `open()`, `read() -> Optional[Tuple[str, frame]]`, `close()`, `is_open`. A live camera has to be released when the trigger ends; a generator cannot express that cleanly.
- `VideoCaptureSource(target, capture_factory=None)`: one class for webcam and video file, both via `cv2.VideoCapture` from the already-pinned `opencv-python`. `VISION_FRAME_SOURCE=0` (digits) means webcam index 0; anything else is a file path. Video files loop from the start at end of file so a demo clip keeps producing frames while the camera is Active. `capture_factory` is injected in tests; the default imports `cv2` lazily.
- `StaticImageSource` stays, adapted to the lifecycle, so the current `test_media/` flow still works when `VISION_FRAME_SOURCE` points at a directory.
- `PiCameraSource`: placeholder. `open()` raises a clear error that the Pi stream is T18. This is the incomplete feature behind the flag.
- `build_frame_source(settings) -> FrameSource`: `FEATURE_PI_CAMERA` on returns `PiCameraSource`; off (the default) returns `VideoCaptureSource` or `StaticImageSource` from `VISION_FRAME_SOURCE`.

`detector.py` keeps only `ThreatDetector`, with `ultralytics` imported inside `__init__`. Its behavior (0.5 threshold, `(class, confidence)` tuples) does not change.

### Posting detections

- Each kept detection posts `POST /threat-events` with `object_class` (raw COCO name from YOLO, as today), `confidence_score`, `camera_id = VISION_CAMERA_ID`, `status = Pending`, and no `source_id`. Then one `POST /system-logs` with `module = vision`, as today.
- New `DetectionThrottle`: post a given class at most once per `VISION_EVENT_COOLDOWN_SECONDS` (default 30). Without it a webcam at 5 fps would write roughly 10 rows per second per person in frame.
- Vision events have no `source_id`, so they never feed `CorroborationTracker` and cannot activate a camera. That keeps corroboration OSINT-only (invariant 6) and avoids a feedback loop.
- Frames are never written to disk or sent to the API. Only class name, score, and camera id leave the process (same as today, `docs/OWASP_AUDIT.md` privacy row).

### API client changes (`vision/vision_client.py`)

- Add `get_camera_state(camera_id) -> Optional[Dict]` (None on 404, raises on other errors).
- Re-authenticate once and retry when a request returns 401. Tokens expire after `JWT_ACCESS_TOKEN_MINUTES` (30 in `scripts/check`), and the runner is long-lived. This is client-only; `backend/app/auth.py` is untouched. `ai-brain/osint_client.py` has the same gap; that is a separate task, not part of T16.
- Remove `set_camera_state()` and `post_camera_state()` so nothing in `vision/` can write camera state. Update `backend/tests/test_vision_client.py`: drop the three `set_camera_state` tests, add tests for `get_camera_state` (200, 404, 500) and the 401 retry.

### `vision/main.py`

Becomes wiring only: load `.env`, read settings, build client, detector, and source, call `VisionRunner.run()`. `VisionPipelineApp`'s activate/dormant logic is deleted.

## Environment variables (`vision/.env.example`, same change)

| Variable | Default | Meaning |
| --- | --- | --- |
| `FEATURE_PI_CAMERA` | `false` | `1`, `true`, `yes`, `on` selects the Pi source (placeholder until T18). Parsed like `FEATURE_LIVE_OSINT` in `ai-brain/osint_settings.py`. |
| `VISION_CAMERA_ID` | `1` | Camera row to watch and to put on threat events. |
| `VISION_FRAME_SOURCE` | `0` | Webcam index (digits), video file path, or image directory. |
| `VISION_STATE_POLL_SECONDS` | `2` | How often to check the camera mode. |
| `VISION_EVENT_COOLDOWN_SECONDS` | `30` | Minimum gap between two events of the same class. |

Existing `BASE_URL`, `VISION_API_USERNAME`, `VISION_API_PASSWORD` stay. Invalid numbers fall back to the default with a warning, as `osint_settings.py` does. Settings live in a new `vision/vision_settings.py`.

## Tests (`vision/tests/`, no network, no model, no camera)

All tests use a `FakeDetector` (scripted detections), a `FakeFrameSource` (counts open/close, yields synthetic arrays or plain objects), a fake capture object for `VideoCaptureSource`, and a fake client or mocked `requests`. `conftest.py` puts `vision/` on `sys.path`, like `ai-brain/tests/conftest.py`.

1. Dormant camera: no `open()`, no detection, no posts.
2. Dormant then Active: source opens, detections post with the configured camera id and status Pending.
3. Active then Dormant: source closes; no posts after the switch.
4. Camera 404: warning logged, keeps polling, never calls POST or PUT on `/camera-states`.
5. Vision never writes camera state in any test (fake client fails the test on any camera write).
6. Throttle: same class twice inside the cooldown posts once; after the cooldown posts again; two classes post independently.
7. Frame pacing follows the row's fps (checked through the injected sleep).
8. `build_frame_source`: flag off with digits gives webcam index, a file path gives video, a directory gives static images; flag on gives `PiCameraSource`. Flag parsing for each accepted spelling and unknown values.
9. `VideoCaptureSource`: fails clearly when the capture cannot open; loops a file at end; `close()` releases the capture.
10. `PiCameraSource.open()` raises the T18 message and the runner exits 1 without crashing.
11. API unavailable mid-run: logged, the loop keeps polling, source is released.
12. `KeyboardInterrupt` closes the source and returns 0.

Coverage: the issue asks for at least 60 percent. The OSINT venv has no `pytest-cov`, but the backend venv does, so I will run `.venv/backend/bin/pytest vision/tests --cov=vision` locally and attach the result to #34. CI does not measure vision coverage; adding `--cov-fail-under` there is a `ci.yml` change and would need its own plan.

`scripts/check` runs `vision/tests` with the OSINT venv. That venv has `pytest`, `requests`, and `python-dotenv` but not `cv2` or `ultralytics` (checked). Because sources and the detector import those lazily, the tests run there with no new dependency.

Optional, only once T02 is merged: one `e2e` test that reuses the T02 harness, lets OSINT corroborate, then runs `VisionRunner` with a fake detector and `max_cycles` and asserts a vision threat event exists with `camera_id=1`.

## Risks

- Seed sets camera 1 `Active`, so vision starts capturing right after seeding. Run `scripts/demo_reset.sh` (T14) or set the camera Dormant in the console before a demo. Documented in the vision README.
- Nothing returns the camera to Dormant after a corroboration, so a webcam can stay on until an operator acts. Out of scope here; see Open questions.
- macOS asks for camera permission the first time OpenCV opens the webcam. The demo machine needs that granted once.
- Vision posts raw COCO names (`car`, `truck`) while OSINT will post shared classes after T01 (`vehicle`). The console shows both. Mapping is not required for corroboration because vision does not corroborate.
